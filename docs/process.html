How the AI was used

Under the course rules an AI is the primary author of the code, the documentation and this website. The team owns the hardware, the decisions and the evidence: every claim that matters is checked on the real circuit.

Who does what

The AI writes

The Pi program in C and ARM assembly, the iPhone app, the schematic and wiring table, the documentation, the analysis scripts and this site. Tool: Claude Code (Anthropic), model Claude Opus 5.5.

The team decides

Answers the AI's questions before each plan, approves or changes the plan, and makes the design choices the plan leaves open.

The team verifies

Builds the circuit, runs every program on the Pi, takes the measurements and test data, and reports the results back to the AI.

The working cycle

  1. Plan. At the start of each checkpoint the AI reads the specification and the existing code, asks the team its open questions, and writes a plan. The approved plan is saved in the ai-log folder.
  2. Build. The AI writes the code and documents on a Mac and checks what it can there: make sim runs the motor logic, the protocol parser and the IR arithmetic against stand-ins for the hardware, and make asmcheck confirms the assembly builds for ARM.
  3. Run on the Pi. The program only builds and runs on the Raspberry Pi, so the team pushes to GitHub, pulls on the Pi, and runs it on the circuit. Bring-up programs (timercheck, bletest, irtest) test one piece at a time.
  4. Report back. The team brings back what actually happened: program output, meter and oscilloscope readings, hand counts, logs. The AI analyses it and changes the code or the documents.
  5. Log. Each session is written up in ai-log: what was asked, what the AI read, what it produced, where it differed from the plan, and what the team found on the bench.

Confirmed on hardware, not assumed

Some examples from the logs of results that came from the bench rather than from the AI:

  • Step timing: the AI's first plan gave the timing thread real-time priority. It then found that Linux pauses a real-time thread that never sleeps, so at Checkpoint 1 the loop ran at normal priority pinned to one core; since Checkpoint 2 it runs at real-time priority and sleeps through the early part of each step period. The team's Checkpoint 1 measurement on the Pi: no step more than 100 µs late at up to 3000 steps/s.
  • Flyback diodes: the AI first said the H-bridge needed external diodes. Re-reading the current datasheet showed internal clamp diodes rated to 1 A; the logs record the correction.
  • Bluetooth dropping after 30 s: traced with btmon on the Pi to an unanswered pairing request, fixed with a "Just Works" pairing agent.
  • The 60 RPM over-reading: the AI's diagnostics showed the propeller was not following the motor, but its explanation was wrong; the team found a loose propeller. See Tests.

Marking human edits

Every source file the AI wrote starts with a header comment ending in (AI-generated). Any change made by a person is wrapped in [HUMAN EDIT] name, date, reason and [END HUMAN EDIT] comments, with the AI's original kept as a comment between them, so grep -rn "HUMAN EDIT" lists every one. This site follows the same rule: a person's change to a page is wrapped in those markers in an HTML comment. Third-party code, such as the Binc Bluetooth library, keeps its own headers.
